1큰 그림 — 3층 + 강제 장치

Karpathy LLM Wiki 패턴(raw → wiki → schema)에 두 가지를 덧붙였다. 모든 수치가 raw에 있는지 스크립트가 검사하고(Grounding Invariant), raw 수정과 규칙 위반은 hooks가 막는다.

설계 원칙 한 줄. 숫자(등급·confidence·카운트)는 사람도 LLM도 손으로 쓰지 않는다. 스크립트가 계산하고, LLM은 판단만 하며, 수정은 사람 승인 후 한 건씩.

2데이터 흐름 — 기사 한 건이 제안서 인용이 되기까지

왼쪽에서 오른쪽으로 흐른다. 각 단계는 산출물 파일이 있고, 다음 단계는 그 파일만 입력으로 받는다. 우회 경로(검색 결과를 바로 use case로 쓰기, 여러 기사를 한 source로 묶기)는 금지다.

단계입력 → 출력실패 시
② 스냅샷URL → raw/*.md (quality: full / partial / llm-extracted / unavailable)403·paywall이면 unavailable로 헤더만 저장, 그 소스의 수치는 "원문 미확인" 표기
③ sourceraw → source 페이지 (tier 1~4, independent true/false)compilation(여러 URL 묶음) 금지. 4월에 만든 4개는 deprecated
④ use casesource들 → 사례 페이지. HR 프로세스 아니면 enterprise-ai/, 법령·리포트면 reference/소스에 없는 항목은 _미공개_. "Workday 또는 자체" 같은 선택지 추정 금지
⑤ 점검lint critical 0 + check_quotes 미확인 0이어야 다음 단계PostToolUse hook이 저장 직후 critical을 돌려보냄
원칙왜
raw 불변검증의 기준점. 바뀌면 인용이 의미를 잃는다
기사 1건 = source 1건어느 수치가 어느 기사에서 왔는지 역추적 가능해야 한다
hedging 보존"검토 중"을 "도입"으로 승격하면 에이전트는 확신도에 반응해 사실로 굳힌다
부재 확인"페이지가 없다"고 말하기 전 grep. LLM의 거짓 부정 방지
자동 수정 금지운영 회고들이 일관되게 반대. 보고 → 승인 → 적용

6운영 도구 — 누가 무엇을 하나

LLM이 하는 일과 스크립트가 하는 일을 분리했다. 스크립트 영역을 LLM이 다시 세지 않고, LLM 영역을 스크립트가 자동 수정하지 않는다.

주기무엇을명령
소스가 생길 때클리퍼로 raw/inbox 저장 → triage → source → use case → grade → lint/hr-ingest raw/inbox
페이지 저장 때critical 점검 (hook 자동)lint.py --quick <file>
주 1회 (수동)grade 재계산 → lint 리포트 → index → 산출물 → digestscripts/weekly.ps1 -NoClaude 또는 /hr-digest weekly
규칙·모델 바꿀 때골든 Q&A 회귀 (무료 오프라인 / LLM)eval_qa.py --offline
클라이언트 자료 받을 때주장 검증, 결과는 internal synthesis/hr-verify "…"
